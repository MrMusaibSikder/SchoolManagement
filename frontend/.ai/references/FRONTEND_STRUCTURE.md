**Two deliberate deviations from the original plan, now the real
convention — don't "fix" these back, they're working and reasonable:**

- **No `routes/`, `providers/`, or `constants/` folders.** Routes live
  directly in `App.tsx`, the QueryClient is created directly in `main.tsx`.
  This is fine at the current size. Revisit only if `App.tsx`'s `<Routes>`
  block gets unwieldy (~30+ routes) — at that point, split into
  `routes/public.routes.tsx` / `routes/protected.routes.tsx` as originally
  planned, but don't do it preemptively.
- **CORS is handled via a Vite dev proxy** (`vite.config.ts` → `server.proxy`),
  not a backend `AddCors` policy. `API_BASE_URL` defaults to the relative
  `/api`, which the proxy forwards to `https://localhost:7083`. This avoids
  CORS, mixed-content, and self-signed-cert issues entirely in dev. **This
  only works for `npm run dev`** — a production build served from a
  different origin than the API will still need real CORS configured on the
  backend, or must be reverse-proxied at the same origin. Not urgent now.

# 2. The established per-feature shape

Based on `src/features/auth/` exactly as built. Not every module needs every
subfolder — only auth needs `context/`+`store/` (session persistence is a
cross-app concern). Most CRUD modules need only `api/`, `hooks/`, `pages/`,
`schemas/`, `types/`, and optionally `components/`.

```
features/{name}/
├── api/
│   └── {name}.api.ts          # thin axios wrappers, one function per endpoint — import
│                               #   authApiClient from "@/lib/api/auth-client" (never public-client,
│                               #   that's landing-only)
├── components/                # feature-local UI only — reach for src/components/ui first (shadcn)
├── hooks/
│   └── use{Action}.ts         # one hook per user action/query — TanStack Query wrapping the api/ call
├── pages/
│   └── {Name}Page.tsx         # route-level component, composes hooks + components
├── schemas/
│   └── {action}.schema.ts     # Zod schema, mirrors the backend DTO's validation rules exactly
├── types/
│   └── {name}.types.ts        # interfaces mirroring backend DTOs field-for-field — see
│                               #   API_REFERENCE_AUTOGENERATED.md, never invent/omit a field
└── index.ts                   # public exports (pages + anything another feature legitimately needs)
```

**Auth-only extras** (do not copy these into other modules unless they
genuinely need persisted, app-wide state — most won't):
```
features/auth/
├── context/
│   ├── auth-context.ts        # React Context definition
│   └── AuthProvider.tsx       # wraps <App>, restores session on mount, exposes login()/logout()
├── store/
│   └── auth.store.ts          # localStorage read/write/clear + expiry check — the ONLY place
│                               #   that touches localStorage for the session
└── components/
    └── ProtectedRoute.tsx     # redirects to /login if !isAuthenticated, preserves `from`
```

**Still to add to `features/auth/`** (see §0 item 3):
```
├── api/current-user.api.ts    # getCurrentUserProfile() → GET /api/CurrentUser/profile
├── hooks/useCurrentUser.ts    # TanStack Query hook, call on app load if a valid session exists
└── components/PermissionGuard.tsx   # hides children unless session.permissions includes the given string(s)
```
Once this exists, `AuthSession`/`auth.types.ts` also needs a `permissions: string[]` field added alongside the existing `roles: string[]`.

Every ⬜ list route generally also needs `/:id` (detail), `/new` (create),

create/edit at all).

All new protected routes go inside the same `<ProtectedRoute><AppShell>`
block already in `App.tsx` — don't create a second wrapper.

# 5. Build-order dependency sanity-check

Don't start a feature before what it depends on exists and is stable:

- `student` needs `school-class`, `section`, `guardian` (searchable dropdowns)
- `exam-schedule` needs `exam`, `subject`
- `mark-entry` needs `exam-schedule`, `student`
- `exam-result` needs `mark-entry`, `grade-setup`
- `final-result` needs `exam-result`, `exam-weight-setup`
- `invoice` needs `student`, `fee-structure`, `academic-year`
- `payment` needs `invoice`
- `receipt` is created automatically by `payment` — no standalone "create" page, only detail/PDF/void
